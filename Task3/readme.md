## Текущее состояние взаимодействий:

- core-app каждые 15 минут синхронно вызывает REST API ins-product-aggregator для обновления локальной копии данных о продуктах и тарифах.

- ins-comp-settlement раз в сутки (ночью) синхронно вызывает ins-product-aggregator для аналогичного обновления своих локальных данных.

- ins-comp-settlement раз в сутки вызывает REST API core-app для получения списка оформленных за день страховок.

## Выявленные проблемы и риски, которые связаны с планируемым ростом нагрузки:

1) Синхронная связность и хрупкость – при сбоях или задержках в работе ins-product-aggregator (например, из-за медленных ответов страховых компаний) оба сервиса-потребителя (core-app и ins-comp-settlement) могут получать ошибки или таймауты, что приводит к несвежести данных и сбоям в оформлении страховок.

2) Избыточная нагрузка на агрегатор – при увеличении числа страховых компаний (с 5 до 10) время ответа ins-product-aggregator может возрасти, а частота опросов (core-app – 96 раз в сутки, ins-comp-settlement – 1 раз) останется прежней, но каждый запрос будет дольше обрабатываться и потреблять больше ресурсов. Пиковая нагрузка на агрегатор может привести к его деградации.

3) Несогласованность данных – локальные копии в core-app и ins-comp-settlement обновляются с разной периодичностью (15 минут против 24 часов). Из-за этого отчётные данные ins-comp-settlement могут основываться на устаревших тарифах, что грозит ошибками в расчётах с партнёрами.

4) Потеря данных при сбоях – если в момент опроса core-app или ins-comp-settlement агрегатор недоступен, данные не обновляются, и сервисы работают со старыми копиями. Для ins-comp-settlement это критично, так как реестр формируется раз в сутки, и пропуск обновления может привести к некорректным реестрам.

5) Масштабирование опросов – при росте числа инстансов core-app (горизонтальное масштабирование) каждый инстанс будет независимо опрашивать агрегатор, умножая нагрузку. 

6) Отсутствие гарантий доставки – текущий подход не гарантирует, что событие (например, оформление страховки) будет обязательно доставлено в ins-comp-settlement. При сбое core-app во время передачи или в момент формирования ответа данные могут быть потеряны.


## Предлагаемые решения на основе Event-Driven Architecture
Для устранения указанных проблем предлагается внедрить асинхронное взаимодействие на основе событий с использованием брокера сообщений (например, Apache Kafka). Это позволит:

- Ослабить связность – сервисы перестанут зависеть от синхронных вызовов и будут обмениваться событиями через брокер.

- Гарантировать доставку – применение паттерна Transactional Outbox обеспечит атомарность записи в БД и публикации события.

- Снизить нагрузку – вместо периодических опросов потребители будут получать только изменившиеся данные, а брокер может буферизировать сообщения и отдавать их по мере готовности потребителей.

- Улучшить согласованность – все заинтересованные сервисы будут получать обновления практически в реальном времени (с небольшой задержкой, определяемой производительностью брокера).

### Какие взаимодействия перевести на Event-Streaming
1) Обновление данных о продуктах/тарифах
Источник: ins-product-aggregator (получает данные от страховых компаний).
Событие: ProductCatalogueChanged (содержит информацию о том, какие продукты/тарифы изменились).
Потребители: core-app, ins-comp-settlement.
Реализация: в ins-product-aggregator добавляется сервис периодического опроса API страховых компаний. При получении ответов от страховых компаний ins-product-aggregator  публикует события об изменениях. Потребители обновляют свои локальные реплики асинхронно. 

2) Оформление страховок
Источник: core-app.
Событие: InsurancePolicyCreated (содержит все данные о новой страховке).
Потребители: ins-comp-settlement (для формирования реестра), а также потенциально другие сервисы (например, аналитика).
Реализация: при успешном оформлении страховки core-app в рамках той же транзакции БД записывает событие в outbox-таблицу. Отдельный компонент (outbox publisher) читает outbox и отправляет события в Kafka. ins-comp-settlement подписывается на топик и сохраняет данные в своей БД для последующей обработки (формирование реестра раз в сутки теперь может быть простым чтением из своей БД, без запросов к core-app).

### Использование паттерна Transactional Outbox
Необходимо применять Transactional Outbox для гарантии, что каждое бизнес-событие (например, создание страховки) будет доставлено в брокер ровно один раз, даже при сбоях. Схема работы:

- В сервисе-источнике (core-app) создаётся таблица outbox в той же базе данных.

- При выполнении бизнес-операции (вставка записи о страховке) в той же транзакции в таблицу outbox добавляется запись с событием.

- Отдельный процесс (может быть реализован как отдельный модуль в сервисе или как отдельный микросервис) периодически опрашивает outbox, отправляет события в Kafka и помечает их как отправленные (или удаляет). При сбоях процесс перезапускается и отправляет неотправленные события, гарантируя at-least-once доставку. Потребители должны быть идемпотентны для обработки дублей.

Для ins-product-aggregator также потребуется outbox, он будет генерировать события об изменениях на основе данных, полученных от страховых компаний. 

Обновлённая диаграмма контейнеров
Новая диаграмма добавляет компоненты для событийного взаимодействия:

Kafka cluster – распределённый брокер сообщений, размещённый во всех трёх зонах доступности для отказоустойчивости (топики с репликацией 3).

Outbox-таблицы в базе данных core-app.

Outbox Publisher – компонент (может быть реализован как отдельный сервис или как модуль внутри core-app), который забирает события из outbox и отправляет в Kafka.

Событийные потоки:

ins-product-aggregator → Kafka (топик product-catalogue-changed) – через outbox.

core-app → Kafka (топик insurance-policy-created) – через outbox.

Kafka → core-app (подписка на product-catalogue-changed).

Kafka → ins-comp-settlement (подписка на product-catalogue-changed и insurance-policy-created).
